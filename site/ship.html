Ship workflow

orbit ship (or plain orbit in a TTY) guides deploy by scope so you only log into providers you are shipping.

Project type

Choice When Providers
API / backend Workers API, Fly app, similar One backend provider
Static site / docs Marketing or docs frontend One frontend provider
Full-stack API and docs in one session Backend + frontend

When both Cloudflare and Vercel are detected, the default is API / backend. Full-stack is explicit so API-only work does not force a Vercel login.

Provider

Orbit lists providers detected via wrangler.toml, vercel.json, fly.toml, and netlify.toml. Pick the match for your project type.

Actions

After scope is saved, the menu offers login, configure, secrets, deploy, and status. Existing CLI sessions are checked before browser OAuth.

If this scope already deployed successfully, you get an Already deployed menu: open URL, view status, secrets, or confirm a re-deploy.

Scope file

Active intent lives in .orbit/state.json:

{
  "environment": "production",
  "ship": {
    "intentId": "api_backend",
    "label": "API / backend — Cloudflare",
    "providers": ["cloudflare"]
  }
}

Change scope by running orbit ship again with a different project type or provider set.

Full-stack notes

Full-stack usually deploys the API first, then docs. With Cloudflare and Vercel, Orbit can set VITE_API_URL on Vercel from the Worker URL before the Vercel phase.

API-only production is the supported happy path in v0.2.x. Treat full-stack as beta until both providers are dogfooded end to end.
