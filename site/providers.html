Providers

Orbit detects provider config in your tree and orchestrates official CLIs. Detection is not the same as active ship scope.

Detection

ProviderDetectionTypical role
Cloudflarewrangler.toml (root or apps/api)Workers API, D1
Vercelvercel.json / Next / Vite markersStatic / docs / Next.js
Fly.iofly.tomlApps / containers
Netlifynetlify.tomlStatic sites

Stack deploy order: Cloudflare → Fly → Vercel → Netlify.

Cloudflare

Requires wrangler. Orbit runs whoami (JSON), create D1 + patch database_id on configure, migrate + deploy phases, and orbit secrets.

Configure requires a D1 database_name in wrangler.toml. Deploy can skip migrate without D1; configure cannot. 

# Secrets (set via `wrangler secret put`):
# API_KEY_PEPPER, GITHUB_TOKEN

CORS_ORIGINS under [vars] feeds status recommendations. After changing vars, re-deploy the Worker.

Vercel

Configure links the project and hints missing VITE_* from .env.example (does not invent values). Full-stack CF+Vercel deploys can auto-wire VITE_API_URL after the Worker URL is known; orbit wire does the same alone.

Fly.io and Netlify

Detected from their config files. Ship treats Fly as API / backend and Netlify as static frontend. Prefer each provider’s own docs for advanced flags.

Scope vs detection

A monorepo can detect Cloudflare and Vercel while ship scope stays API-only. Status then skips Vercel until you choose Static site or Full-stack. Bare orbit deploy still deploys every detected provider.

Common fixes

  • Doctor fails: install the scoped CLI, fix PATH, then orbit login
  • Configure without D1: add [[d1_databases]] with database_name
  • Worker 1101 / 500: orbit secrets --put …
  • Health 404: use the path from status (often /v1/health)
  • Wrong providers on deploy: use --provider or ship scope, not bare orbit deploy
  • Mid-deploy failure: orbit logs --failed then orbit retry
